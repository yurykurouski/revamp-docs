# Automated tests expertise: Revamp — стратегия и архитектура автотестов

22 ноября 2026

Документ для экспертной оценки критерия **Automated tests** (`04f-testing/auto-tests.md`). Разделы 1–7 описывают тестовый набор и стратегию (минимальные требования 1–8), раздел 8 — покрытие и известные пробелы с тикетами, раздел 9 — обоснование решений и рекомендации (максимальные требования), раздел 10 — сводная таблица соответствия.

## 1. Репозиторий и запуск

* Код и тесты: [yurykurouski/revamp-dev](https://github.com/yurykurouski/revamp-dev) (публичный). CI: вкладка **Actions**, workflow `CI`, job **Gates**.
* Требования: Node 20+, Docker (для `npm run setup`; самим тестам Docker не нужен).

```bash
npm run setup     # один раз: зависимости, Playwright Chromium, .env, сборка пакетов
npm test          # весь набор: vitest run из корня
npm run test:watch
npx vitest run apps/api            # одна область
npx vitest run -t "tenant"         # по имени теста
```

Тесты не ходят во внешние сервисы: в `vitest.config.ts` LLM-провайдеры отключены (`MVP_LLM_PROVIDER=''`, `CLAUDE_CLI_PATH` указывает в никуда), `JWT_SECRET` — тестовый, MongoDB поднимается в памяти (`mongodb-memory-server`), почта и очереди подменены. Запуск не трогает локальную базу разработчика.

## 3. Стратегия: какие тесты и зачем

Набор построен как пирамида: много быстрых unit-тестов на чистой логике, интеграционные тесты на стыках, где ошибки дороже всего (HTTP ↔ сервис ↔ база ↔ очередь), и отдельные тесты в настоящем браузере там, где без него поведение не проверить.

| Уровень | Чем | Примеры |
| --- | --- | --- |
| **Unit** | Vitest, моки моделей и очередей через `vi.mock` | `scoring.service`, `site-complexity`, `css-sanitizer`, `lead-status` (машина состояний), `password`, `token` |
| **Integration: API** | supertest против настоящего Express-приложения | `api.routes`, `auth.routes`, `organization.routes`, `track.routes`, `route-auth` |
| **Integration: база** | `mongodb-memory-server`, MongoDB 7.0 replica set (как в проде, с транзакциями) | `real-mongo.spec.ts` (уникальность `leadId` при 20 параллельных upsert), `tenant-isolation.spec.ts` (две студии, HTTP → база) |
| **Integration: очереди** | BullMQ-обработчики с подменённым соединением | `audit.worker`, `ai.worker`, `email.worker`, `deploy-page`, enqueue-or-revert в `email-enqueue` |
| **Браузер (настоящий Chromium)** | Playwright как библиотека, локальные HTML-фикстуры | `cookie-consent.service` (баннеры cookie), `mvp-page-finish.browser` (готовая страница MVP в браузере) |
| **Компоненты UI** | happy-dom + React, `createElement` | `ReviewQueuePage`, `AppShell`, `AuthPage`, `TeamPage`, `LeadReview` и др. |
| **Сквозной сценарий пайплайна** | 20 конфигураций сайтов из 4 ниш с крайними случаями | `e2e-20-sites.spec.ts` (REV-19): аудит → оценка → MVP → проверки → письмо, ≥ 18/20 сайтов проходят |
| **Архитектурные тесты** | Статический анализ исходников в тесте | `tenant-guard.spec.ts` — падает на любом запросе к моделям студии мимо слоя `scopeFor()`; `route-auth.spec.ts` — падает на неклассифицированном маршруте |

Браузерного e2e-набора (Playwright против запущенных дашборда и API) пока нет — см. раздел 8.

## 4. Структура и соглашения

* Тесты лежат рядом с кодом: `<папка>/__tests__/<модуль>.spec.ts` (например `apps/api/src/services/__tests__/lead.service.spec.ts`). Пакеты без `src/` — `packages/validation/__tests__/`.
* Расширение — только `.spec.ts` / `.test.ts` (`include` в `vitest.config.ts`). Компоненты React в тестах создаются через `createElement`, поэтому `.spec.tsx` не нужен; такой файл раннер не подхватит, это зафиксировано в правилах агентов.
* Имя файла — имя тестируемого модуля; браузерные тесты помечены суффиксом `.browser.spec.ts`.
* `describe` называет поведение и тикет, который его ввёл: `describe('Lead state machine (REV-62)')`, `describe('a studio sees only its own records (REV-209)')`. `it` — утверждение о поведении, а не о реализации («answers 401 to a forged token on a guarded route»).
* Общие помощники — рядом с тестами, без `.spec`: `authed-request.ts`, `route-table.ts`, `loopback-server.ts`, `packages/db/src/testing/mongo-memory.ts`, фикстуры в `services/__tests__/fixtures/`.
* Общая настройка — `vitest.setup.ts` (тесты дашборда начинают с сессии владельца; тест про роли задаёт свою).

## 5. Бизнес-критичные области

| Область | Почему критична | Чем покрыта |
| --- | --- | --- |
| **Human-in-the-Loop** | Письмо уходит только после одобрения оператора | Тесты одобрения в `api.routes.spec.ts` (транзакция, постановка в очередь или откат статуса при недоступной очереди), `email.worker.spec.ts` (воркер не отправляет без одобренной кампании) |
| **Машина состояний лида** | Статус не должен идти назад от поздних задач и трекинга | `lead-status.spec.ts`: каждый статус достижим из `QUEUED`, `UNSUBSCRIBED` финальный, запрещены «короткие пути»; атомарные фильтры по статусу в сервисах и воркерах |
| **Аутентификация и роли** | Доступ к данным студии | `route-auth.spec.ts` (каждый маршрут: публичный или 401, поддельный токен, роли owner/operator/viewer), `requireAuth.spec.ts`, `auth.service.spec.ts`, `roles.spec.ts` |
| **Изоляция студий** | Студия не видит чужие лиды | `tenant-isolation.spec.ts` (реальная база: чужая запись = 404, ничего не меняется), `tenant-scope.spec.ts`, `tenant-guard.spec.ts`; воркеры отказываются от задачи с чужим `tenantId` |
| **Валидация входа** | Все тела запросов и ответы LLM проходят Zod | `packages/validation/__tests__` (валидные, невалидные, граничные значения), `validate.spec.ts` |
| **Единый формат ошибок** | Клиент читает только `error.code` | `errorHandler.spec.ts`, коды ответов в тестах маршрутов |
| **Детерминированные метрики** | Метрики и контакты считает код, не LLM; провал измерения не заменяется подставным значением | `vitals.service`, `axe.service`, `site-content.extractor`, `mvp-grounding` (цитаты MVP сверяются с исходным сайтом) |
| **Целостность данных** | Не больше одного MVP и одной кампании на лид | `real-mongo.spec.ts`, `lead-children-unique.spec.ts`, `retry-duplicate-key.spec.ts`, миграции `lead-children-migration` |
| **Сбои задач** | Повторы, финальная попытка, зависшие задачи | `audit-failure.spec.ts`, `generation-failure.spec.ts`, `queued-lead-repair`, `stuck-audit-backfill` |

## 6. Техники

* **Моки внешних сервисов.** LLM, Vision-модель, SMTP, Google Places и S3/MinIO подменяются на границе адаптера (`IEmailProvider`, клиент LLM), а не внутри логики. В рантайме моков нет (правило REV-45): тестовые двойники живут только в тестах.
* **Тестовые двойники моделей и очередей.** `vi.mock` для Mongoose-моделей и `bullmq` в unit-тестах сервисов; те же сценарии с реальной базой — в интеграционных тестах, чтобы мок не скрыл ошибку схемы (Mongoose в strict-режиме молча отбрасывает необъявленные поля — это проверяется только на реальной базе).
* **In-memory инфраструктура.** `mongodb-memory-server` с replica set (транзакции работают как в проде), loopback HTTP-сервер для тестов сетевых провайдеров.
* **Фикстуры.** HTML-страницы для браузерных тестов и генератора страниц (`fixtures/page-gen`), демо-набор данных (`demo-dataset.spec.ts` проверяет, что каждый статус лида в нём представлен).
* **Тестирование конкурентности.** 20 параллельных upsert на один лид → одна запись (`real-mongo.spec.ts`), параллельные первые публикации с одним slug.
* **Фейковые таймеры.** Опрос React Query и интервалы дашборда (`vi.useFakeTimers`), без реальных ожиданий.
* **Архитектурные проверки в тестах.** `tenant-guard.spec.ts` разбирает исходники API и падает на прямом запросе к моделям студии; у самого сканера есть тесты на ложные срабатывания.

## 7. CI и quality gates

Workflow `.github/workflows/ci.yml`, job **Gates**, запускается на каждый PR, push в `main` и вручную; это обязательная проверка защиты ветки `main` (без неё не смержить):

1. `npm ci` (с кэшем бинарника MongoDB 7.0.14 для тестов)
2. `npx playwright install --with-deps chromium` — для браузерных тестов
3. `npm run build:packages`
4. `npm run typecheck` — TypeScript во всех workspace
5. `npm run lint` — ESLint, 0 ошибок
6. `npm test` — весь набор на чистом ubuntu-latest
7. `npm run build`

Последние 18 запусков на `main` — все успешны. Тот же набор гейтов обязателен локально перед каждым PR (`AGENTS.md` §4), политика тестов — `AGENTS.md` §3.2.5: каждая новая или изменённая функциональность покрывается тестами в том же PR.

## 9. Обоснование решений и рекомендации

### Почему так

| Решение | Альтернатива | Почему выбрано |
| --- | --- | --- |
| Один Vitest на весь монорепозиторий | Jest + отдельные конфиги по пакетам | Нативный ESM и TypeScript без трансформаций, один `npm test`, алиасы пакетов на исходники (тесты не ждут сборки) |
| Тесты рядом с кодом в `__tests__` | Отдельное дерево `tests/` | Тест и модуль меняются в одном PR; видно, у какого модуля тестов нет |
| `mongodb-memory-server` с replica set | Моки моделей везде; общая dev-база | Транзакции и уникальные индексы работают только на настоящем MongoDB; общая база ломала бы параллельные прогоны и данные других разработчиков |
| happy-dom для компонентов | jsdom; Testing Library | Быстрее jsdom, достаточно для рендера и событий; браузерный уровень добавляется отдельно (REV-213) |
| Playwright-Chromium в тестах воркеров | Только моки страниц | Баннеры cookie и готовую страницу MVP нельзя честно проверить без настоящего браузера |
| Архитектурные тесты (`tenant-guard`, `route-auth`) | Code review | Правило «каждый запрос через scope студии» проверяется на каждом PR автоматически, а не памятью ревьюера |

### Как тесты помогли

Каждый исправленный дефект получает регрессионный тест с номером тикета в `describe`; таких тикетов в наборе — 94. Примеры:

* **REV-201** — у лида могло появиться два MVP или две кампании. Исправление — уникальный индекс `leadId`, upsert по `{ leadId }` и миграция; регрессионный тест с 20 параллельными upsert на реальной базе проверяет, что запись остаётся одна.
* **REV-209** — изоляция студий: `tenant-guard.spec.ts` не даёт добавить запрос мимо `scopeFor()`, `tenant-isolation.spec.ts` проверяет весь путь HTTP → база для двух студий.
* **REV-206 / REV-207** — `route-auth.spec.ts` падает, если новый маршрут не помечен как публичный или защищённый, и проверяет права каждой роли.
* **REV-100** — провалившееся измерение больше не подменяется значением по умолчанию; тесты сервисов аудита требуют, чтобы значение отсутствовало и была записана ошибка.
* **REV-62** — одна машина состояний вместо локальных списков статусов: тесты закрепляют запрет прежних «коротких путей» (вовлечённость до отправки письма, движение назад) и проверяют, что каждый статус достижим.

### Рекомендации

1. Подключить покрытие с порогом 70% и бейдж (REV-179) — первым делом.
2. Добавить 1–2 браузерных e2e-сценария (REV-213) и запускать их в CI на отдельной базе.
3. Property-based тесты для машины состояний и contract-тест ответов API по спецификации (REV-215).
4. После покрытия — мутационное тестирование (Stryker) на `packages/validation` и сервисах API, чтобы проверить силу утверждений, а не только процент строк.
5. Нагрузочный прогон перед продакшен-развёртыванием (REV-216, REV-211).
